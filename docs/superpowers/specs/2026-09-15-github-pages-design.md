# Выкладка на GitHub Pages

Спецификация инфраструктурной работы. Дата: 2026-09-15. Пункта в `PLAN.md` нет:
задача пришла вопросом владельца и решена в разборе того же дня.

## 1. Зачем

Приложение существует только на машине разработчика. Показать его ученику,
учителю или самому себе с другого устройства нельзя: нужно поднять `npm run
dev`. Тренажёр при этом ровно того рода, который выкладывается одной командой —
статика без сервера, без базы, без ключей.

## 2. Почему именно Pages

Проверено по коду, а не по памяти:

- Роутера нет — `src/App.tsx` переключает экраны состоянием. Значит нет и
  глубоких ссылок, а с ними отпадает `404.html`, которым обычно чинят SPA на
  Pages.
- Во время раунда сети нет (`AGENTS.md`), запросов в `src` не найдено вовсе.
- Геометрия карты попадает в бандл на сборке (`svg?raw`), шрифты режутся у нас
  и лежат в `src/assets`. Ничего не догружается со стороны.
- `dist` — 16 МБ при пределе Pages в 1 ГБ на сайт и 100 ГБ трафика в месяц.

Иными словами, приложение уже статическое; недостающее — базовый путь и работа
выкладки.

## 3. Решения владельца от 2026-09-15

1. **Репозиторий становится публичным.** Pages на приватном репозитории требует
   плана Pro и выше. Цена принята вместе с последствием: история коммитов уходит
   в открытый доступ необратимо.
2. **Адрес — проектный сайт** `https://bronik04.github.io/china-studies-trainer/`.
   Свой домен и корневой сайт `bronik04.github.io` отклонены: первый требует
   покупки домена, второй — отдельного репозитория и отдаёт личный адрес под
   один проект.
3. **Выкладка — работа в `checks.yml`**, а не отдельный файл: сборка одна на
   двоих, и на сайт физически не может попасть то, что не прошло проверки.
4. **Базовый путь одинаков в разработке и в бою.** Расхождение между ними — та
   самая ошибка, которую эта работа и чинит; прятать её от себя же не стоит.

## 4. Базовый путь

`vite.config.ts` получает `base: '/china-studies-trainer/'` безусловно — без
ветвления по `command`. Vite подставит его сам в `index.html`, в имена кусков
сборки, в шрифты и в `url()` внутри CSS. Сервер разработки станет отдавать
приложение по `localhost:5173/china-studies-trainer/` и перебрасывать туда с
корня; предпросмотр, ходящий на корень, переброс отработает.

Ручных адресов в коде ровно два, оба — снимки коллекций:

| Где | Сейчас |
| --- | --- |
| `src/ui/photo-source.ts:21` | `` `/photos/${photoId}-${ширина}.webp` `` |
| `src/ui/CollectionImage.tsx:73` | `` `/photos/${photo.id}-${width}.webp ${width}w` `` в `srcSet` |

Править оба — значит поселить знание о базовом пути в двух местах, одно из
которых разметка. Вместо этого рядом с `photoSource` появляется вторая функция:

```ts
export function photoSourceSet(photoId: string): string | null
```

Она собирает всю строку `srcSet` — перечисление доступных ширин, — и компонент
про адреса не знает больше ничего. `import.meta.env.BASE_URL` встречается в
одном модуле. Отдельным файлом `photo-source.ts` уже существует по своему
доводу (посторонний экспорт рядом с компонентом ломает обновление на лету);
новая функция ложится туда же по тому же доводу.

`BASE_URL` всегда оканчивается косой чертой, поэтому в шаблоне пишется
`${import.meta.env.BASE_URL}photos/...` — без второй черты.

### Тесты

Нового файла `src/ui/photo-source.test.ts` сегодня нет. Появляется, и проверяет:

- оба адреса начинаются с `import.meta.env.BASE_URL`;
- `photoSource` берёт наибольшую доступную ширину;
- `photoSourceSet` перечисляет все ширины из `PHOTO_CREDITS` и размечает их
  дескриптором `w`;
- обе функции отдают `null` для незнакомого снимка.

Существующие тесты на литерал `/photos/...` не завязаны — проверено поиском,
риска правка не несёт.

## 5. Выкладка

`.github/workflows/checks.yml` получает вторую работу. Строение:

| Работа | Условие | Что делает |
| --- | --- | --- |
| `checks` | как сейчас, любая ветка | линтер, тесты, сборка; в конце `actions/upload-pages-artifact` с `path: dist` |
| `deploy` | `needs: checks` и `github.ref == 'refs/heads/master'` | `actions/deploy-pages` на окружение `github-pages` |

Существенное:

- **Сборка одна.** `deploy` забирает артефакт, а не пересобирает: пересборка
  могла бы разойтись с проверенной.
- **Права выдаются работе, а не файлу.** У файла остаётся `contents: read`;
  `pages: write` и `id-token: write` стоят только в `deploy`. Проверки не должны
  получать право публиковать.
- **Своя `concurrency: pages` с `cancel-in-progress: false`.** Проверки
  отменяются новым пушем намеренно, выкладку обрывать на полпути нельзя.
- **Действия закрепляются по sha** с версией в комментарии рядом — правило этого
  файла, оно не меняется.
- **Шапка-комментарий переписывается.** Утверждение «прогон ничего не публикует
  и никуда не пишет» перестаёт быть правдой; оставить его хуже, чем не иметь
  комментария вовсе.

## 6. Настройка репозитория

Два действия делаются в интерфейсе GitHub владельцем, кодом они не выражаются:

1. Репозиторий → публичный.
2. Settings → Pages → Source: **GitHub Actions** (не «Deploy from a branch»).

**Порядок обязателен:** оба действия — до слияния в `master`. Иначе первый
прогон `deploy` упадёт на выключенном Pages, и гнать его придётся заново.

## 8. Известные ограничения

- **Открытый репозиторий необратим.** Вернуть его в приватные можно, но уже
  выгруженную историю это не отменит.
- **Сайт публичен при любом плане.** Приватным его делает только Enterprise;
  выбор из раздела 3 на это не влияет.
- **Первая загрузка — 16 МБ,** из них 15 приходится на фотографии коллекций.
  Правило «во время раунда сети нет» не нарушено: снимки прогреваются до первого
  вопроса. Но с медленного мобильного первый вход будет заметно небыстрым.
  Разбиение фотографий по требованию — отдельная работа, в эту не входит.
