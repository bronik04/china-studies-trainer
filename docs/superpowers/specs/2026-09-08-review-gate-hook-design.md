# Ворота ревью: хук, который не пускает в master непроверенное

## Цель

Закрепить правило, которое сейчас держится на памяти: в `AGENTS.md` записано,
что «до слияния в главную ветку изменения проходят ревью и все предусмотренные
проверки», но ничто не мешает слить ветку, которую никто не смотрел. Проверки
(линтер, тесты, сборка) уже закреплены CI — `.github/workflows/checks.yml`
гоняет их на каждый пуш. Ревью не закреплено ничем.

Хук Claude Code делает эту половину правила исполнимой: `git merge` в master
не проходит, пока для сливаемого коммита нет записи о ревью.

## Предусловие

Есть и работает: CI на каждый пуш; сливы делаются локально командой вида
`git checkout master && git merge --no-ff <ветка>`; рабочие деревья в
`.worktrees/`; встроенный скилл `/code-review`, заканчивающийся вызовом
инструмента `ReportFindings`. Git-хуков в репозитории нет, `core.hooksPath`
не настроен, `.claude/settings.json` не существует, а вся папка `.claude/`
игнорируется.

## Решения владельца продукта (2026-09-08)

- Хук — **Claude Code**, не git. Ловит агента; слив, сделанный владельцем
  руками в терминале, проходит без вопросов.
- Хук — **привратник**: сам ревью не запускает и проверок не гоняет, а
  требует записи о том, что ревью было.
- Запись появляется **автоматически** по завершении `/code-review`. Ручной
  команды-обхода нет.
- Ловится **только `git merge` с целью master**. Пуш, `gh pr merge` и прочие
  обходные пути не закрываются: в этом репозитории так не сливают.
- `.claude/settings.json` **разыгнорить** и вести в git, чтобы заслон ехал
  вместе с репозиторием.
- Ревью с находками **открывает ворота**. Хук проверяет факт ревью, а не его
  итог: что делать с замечаниями, решает владелец.

## 1. Два хука

**Записывающий** — `PostToolUse`, матчер `ReportFindings`. Этим инструментом
заканчивается `/code-review`: он вызывается один раз и со списком находок,
пустым в том числе. Хук берёт из полезной нагрузки `cwd`, спрашивает у git
текущий HEAD и ветку и дописывает запись в журнал.

**Ворота** — `PreToolUse`, матчер `Bash`. Разбирает команду; если она сливает
что-то в master, каждая сливаемая ссылка разрешается в sha, и по этому sha
ищется запись в журнале. Сливаются несколько веток — запись нужна каждой. Нет
записи хотя бы у одной — отказ:

```json
{ "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Ветка feat/x (db1dd24) не проходила ревью. Запустите /code-review, затем повторите слияние."
} }
```

В `.claude/settings.json` это две строки:

```json
{ "hooks": {
  "PreToolUse": [ { "matcher": "Bash", "hooks": [
    { "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR/scripts/hooks/review-gate.sh\"" } ] } ],
  "PostToolUse": [ { "matcher": "ReportFindings", "hooks": [
    { "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR/scripts/hooks/review-record.ts\"" } ] } ]
} }
```

`$CLAUDE_PROJECT_DIR` указывает на корень той копии, в которой идёт сессия, —
для рабочего дерева из `.worktrees/` на само дерево. Скрипты лежат рядом с
кодом, значит находятся в любой копии.

Отказ — не запрет: команду, набранную владельцем в собственном терминале,
хук не видит вовсе. Это и есть аварийный выход для экстренного исправления,
которое `AGENTS.md` допускает по решению владельца.

## 2. Журнал

Файл `review-log.json` в **общем каталоге git** — том, что отдаёт
`git rev-parse --path-format=absolute --git-common-dir`. Для основного
каталога это `.git/`, для любого рабочего дерева из `.worktrees/` — тот же
самый `.git/` основного репозитория.

Место выбрано не случайно. Ревью делается в ветке, часто в отдельном рабочем
дереве, а слив — в основном каталоге. Журнал внутри `.claude/` был бы у
каждой копии свой, запись осталась бы в дереве, и ворота в основном каталоге
не открылись бы никогда. Внутри `.git/` файл к тому же не попадает в
индекс по определению — игнорировать его отдельно не нужно.

```json
{
  "version": 1,
  "reviews": [
    { "sha": "db1dd24358cdd82f3dff069562818266b5ead55e",
      "branch": "feat/x", "findings": 2, "level": "high",
      "at": "2026-09-08T07:40:00.000Z" }
  ]
}
```

Записи идут от новых к старым, хвост обрезается до пятидесяти. `findings` и
`level` на решение ворот не влияют — они нужны, чтобы в тексте отказа и при
разборе было видно, каким было ревью. Запись атомарна: временный файл рядом
и `rename`.

Испорченный или нечитаемый журнал — не падение: он трактуется как пустой,
ворота закрываются, и владелец видит внятную причину. Терять здесь нечего,
файл восстановим следующим ревью.

## 3. Как опознаётся слив в master

**Ветка-цель.** Последний `git checkout X` или `git switch X` в той же
командной строке; если такого нет — текущая ветка по `git rev-parse
--abbrev-ref HEAD`. Разбирать строку целиком обязательно: типичная команда
выглядит как `git checkout master && git merge --no-ff feat/x`, и на момент
хука текущая ветка — ещё `feat/x`. Проверка «я сейчас на master» промахнулась
бы ровно в том случае, ради которого всё делается.

Мастер-ветками считаются `master` и `main`. Список — константа в коде: в этом
репозитории ветка одна, а угадывать по `origin/HEAD` значит зависеть от
настройки, которой в свежем клоне может не быть.

**Сливаемые ссылки.** Из отрезка команды, начинающегося с `git merge` и
кончающегося разделителем (`&&`, `||`, `;`, `|`), берутся токены, которые не
являются флагами и не являются значением флага, требующего значения
(`-m`, `-F`, `-S`, `-X`, `--strategy`, `--strategy-option`, `--into-name`,
`--gpg-sign`, `--message`, `--file`). Каждый оставшийся токен проверяется
через `git rev-parse --verify --quiet <токен>^{commit}`: что разрешилось в
коммит — то и сливают.

Ссылок не нашлось — ворота молчат. Это покрывает `git merge --abort`,
`--continue`, `--quit` и слив без аргументов.

**Когда ворота не вмешиваются:**

| Случай | Почему |
| --- | --- |
| цель — не master | обычная работа в ветке, в том числе `git merge master` в ветку |
| в команде нет `git merge` | не наше дело |
| ни одна ссылка не разрешилась в коммит | сливать нечего |
| сливаемая ссылка — сама master-ветка | слив master в master, пустая операция |
| git недоступен или команда git упала | хук не мешает работать из-за собственной поломки |

Последняя строка — осознанный выбор в пользу пропуска. Хук, который начинает
блокировать всё подряд, когда у него самого что-то сломалось, снимают в тот
же день, и вместе с ним пропадает польза.

## 4. Модули и границы

| Файл | Что делает | От чего зависит |
| --- | --- | --- |
| `scripts/hooks/merge-command.ts` | разбор командной строки: цель слияния и список ссылок-кандидатов | ни от чего — чистые функции над строкой |
| `scripts/hooks/review-log.ts` | чтение, дополнение и обрезка журнала | файловая система, путь передаётся снаружи |
| `scripts/hooks/git.ts` | тонкая обёртка над нужными командами git | `child_process`, каталог передаётся снаружи |
| `scripts/hooks/review-gate.ts` | ворота: stdin → решение → stdout | три модуля выше |
| `scripts/hooks/review-record.ts` | запись: stdin → строка журнала | `review-log.ts`, `git.ts` |
| `scripts/hooks/review-gate.sh` | быстрый отсев перед запуском Node | ничего |

Граница, ради которой это разведено: разбор команды не знает ни про git, ни
про файлы, поэтому проверяется таблицей входов и выходов, без временного
репозитория. Журнал не знает, откуда взялся sha. Точки входа только читают
stdin, зовут эти функции и печатают ответ.

**Почему TypeScript и `node`, а не `tsx`.** Ворота срабатывают на **каждой**
команде Bash, и цена запуска — это цена работы. На этой машине: `node -e 0` —
83 мс, `node file.ts` (Node 26 снимает типы сам) — 150 мс, `npx tsx` — 920 мс.
`tsx` исключён. TypeScript при этом остаётся: `tsconfig.node.json` уже
включает `scripts`, значит `npm run build` проверяет эти файлы типами наравне
с остальными, и eslint их видит.

**Почему перед Node стоит `.sh`.** Полторы сотни миллисекунд на каждой команде
Bash — заметная плата за хук, который в 99 случаях из 100 отвечает «не моё
дело». Шелл-обёртка читает stdin, ищет в нём подстроку `merge` и, не найдя,
выходит с нулём за единицы миллисекунд. Отсев нарочно грубый — решает всё
равно разбор в `merge-command.ts`.

## 5. Проверки

| Тест | Что закрепляет |
| --- | --- |
| `merge-command.test.ts` | `git checkout master && git merge --no-ff feat/x` — цель master, ссылка `feat/x`; `git merge master` на ветке — не наш случай; `-m "merge: …"` не принимается за ссылку; `--abort`, `--continue`, `--quit` — ссылок нет; разделители `&&`, `;`, `\|` обрывают отрезок; `git switch master` наравне с `checkout` |
| `review-log.test.ts` | запись дописывается первой; хвост обрезается до пятидесяти; испорченный JSON читается как пустой журнал и не роняет запись; поиск по sha |
| `review-gate.test.ts` | прогон точки входа во временном репозитории: без записи — `deny` с именем ветки и sha в тексте; с записью — тишина; чужая команда — тишина; поломанный git — тишина |
| `review-record.test.ts` | прогон точки входа: после вызова в журнале запись с HEAD и веткой временного репозитория, число находок и уровень сохранены |

Временные репозитории тесты создают в каталоге ОС, а не в проекте.

## 6. Чего хук не делает

Не гоняет линтер, тесты и сборку: это делает CI, и дублировать минуту ожидания
на каждый слив незачем. Не запускает ревью сам. Не ставит git-хуков и не
трогает `core.hooksPath`. Не закрывает пуш и `gh pr merge`. Не хранит ничего,
кроме sha, имени ветки, числа находок и времени.

## 7. Риск, который проверяется живым прогоном

Записывающий хук держится на предположении, что `ReportFindings` вызывается в
сессии, а не внутри субагента, чьи вызовы до хуков сессии не доходят. Если
предположение неверно, запись не появится, и ворота не откроются никогда —
худший вид заслона.

Поэтому в плане реализации отдельным шагом стоит живой прогон `/code-review`
в этом репозитории с проверкой, что в журнале появилась строка. Не появилась —
работа останавливается и владельцу предлагается другой сигнал (`Stop`-хук,
читающий стенограмму), а не обходной путь вроде ручной команды: её владелец
уже отклонил.
